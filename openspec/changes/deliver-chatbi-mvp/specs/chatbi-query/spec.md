# Spec Delta

## Purpose

该能力为本地 ChatBI MVP 提供统一的自然语言查询契约，将业务问题转换为经过约束的 SQL，并返回可展示、可追踪且可诊断的结构化结果。

## ADDED Requirements

### Requirement: 接收并校验业务问题
系统 SHALL 接收 UTF-8 自然语言问题，并在调用模型或数据库之前拒绝空白问题以及超过配置长度上限的问题。

#### Scenario: 提交有效问题
- **WHEN** 客户端提交一个非空且未超过长度上限的业务问题
- **THEN** 系统进入查询处理流程并分配唯一请求标识

#### Scenario: 提交空白问题
- **WHEN** 客户端提交空字符串或仅包含空白字符的问题
- **THEN** 系统返回可识别的输入校验错误且不调用模型和数据库

### Requirement: 编排 Text-to-SQL 查询链路
系统 SHALL 按问题解析、指标知识匹配、Schema 选择、Prompt 构建、SQL 生成、安全校验和数据库执行的顺序处理有效问题，且任何阶段失败时不得继续执行后续有副作用或高成本的阶段。

#### Scenario: 查询成功
- **WHEN** 所有处理阶段均成功
- **THEN** 系统返回生成 SQL、列定义、结果行、行数、耗时和请求标识

#### Scenario: 中间阶段失败
- **WHEN** 模型调用、Schema 选择、安全校验或数据库执行任一阶段失败
- **THEN** 系统停止链路并返回稳定错误码、用户可理解消息和请求标识

### Requirement: 注入业务指标口径
系统 SHALL 在问题命中已配置指标或别名时，将指标定义、公式、数据来源、依赖指标和强制过滤条件纳入 SQL 生成上下文。

#### Scenario: 查询销售额
- **WHEN** 问题包含“销售额”“营收”或“收入”
- **THEN** 生成上下文采用不含税收入和已完成订单口径，并包含必要的汇率换算知识

#### Scenario: 未命中指标
- **WHEN** 问题未匹配任何已配置指标
- **THEN** 系统继续使用 Schema 与通用业务规则生成 SQL，且不伪造指标定义

### Requirement: 选择相关 Schema
系统 SHALL 优先使用表级与字段级语义召回生成精简 Schema；当召回服务不可用或无有效结果时，系统 MUST 回退到受支持业务表的静态 Schema，并在响应诊断信息中标记所用模式。

#### Scenario: 语义召回成功
- **WHEN** 表和字段召回返回超过阈值的候选项
- **THEN** SQL 生成上下文仅包含候选表、必要关联字段和命中的业务字段

#### Scenario: 召回失败后回退
- **WHEN** Embedding 服务不可用、索引缺失或候选结果为空
- **THEN** 系统使用静态 Schema 完成后续处理并将 Schema 模式标记为 `fallback`

### Requirement: 提供稳定查询 API
系统 SHALL 提供版本化 HTTP 查询端点，使用 JSON 接收问题并返回统一响应信封；成功和失败响应 MUST 保持文档化字段结构。

#### Scenario: API 查询成功
- **WHEN** 客户端向版本化查询端点提交有效 JSON 请求
- **THEN** 系统返回成功状态、结构化查询结果和请求标识

#### Scenario: API 请求格式错误
- **WHEN** 请求体不是合法 JSON 或缺少必填问题字段
- **THEN** 系统返回 4xx 状态、输入错误码和字段级错误信息
