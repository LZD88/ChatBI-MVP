# Design

## Context

参见 [proposal.md](proposal.md) 的 Why。现有仓库是平铺的 Python 教学项目：Prompt、模型调用、指标知识、表/字段召回、数据库和评估模块分别存在，但没有应用服务层或 HTTP 入口；`main.py` 仍是脚手架，`database.py` 引用了缺失的 `security.py`，动态 Schema 路径引用了缺失的 `schema_linker.py`，依赖声明也不完整。

MVP 的主要约束是：单机、单用户、MySQL、OpenAI 兼容 Chat/Embedding 接口；能够在召回不可用时降级；任何模型输出在进入数据库前都必须经过确定性的安全边界。项目目前没有已发布 OpenSpec 规格，因此本变更建立第一组产品行为基线。

## Goals / Non-Goals

**Goals:**

- 将已有模块收敛成一个可测试的应用服务，并通过版本化 HTTP API 与 Web 页面提供完整演示链路。
- 用确定性的 SQL 解析与数据库最小权限建立双层只读保护，而不是依赖 Prompt 自律。
- 使新开发者能用锁定依赖、配置模板、演示数据库和明确命令复现环境。
- 保留现有教学模块中有价值的业务口径和评估逻辑，同时为未来替换模型、数据库或前端保留边界。
- 提供足以判断 MVP 是否可交付的自动化测试和固定基准门槛。

**Non-Goals:**

- 不设计账号、租户、RBAC、SSO、审计平台或生产数据源接入。
- 不实现多轮上下文、追问消歧、异步任务队列、结果缓存和复杂可视化。
- 不以本变更支持任意数据库方言；第一版固定 MySQL。
- 不承诺公网部署、水平扩展或高并发 SLA；目标是可靠的本地演示和小规模试用。

## Decisions

### 1. 采用模块化单体和单进程 FastAPI

应用划分为 API/静态页面、应用编排、领域能力和基础设施四层，但在一个 Python 进程中运行。建议目录如下：

```text
chatbi/api              # 路由、请求/响应模型、错误映射
chatbi/application      # ChatBI 查询编排服务
chatbi/domain           # 指标、Schema 选择、SQL 安全契约
chatbi/infrastructure   # LLM、Embedding、Chroma、MySQL 适配器
chatbi/web              # 静态 HTML/CSS/JS
scripts                 # 数据库与索引初始化入口
tests                   # 单元、集成、基准测试
```

选择 FastAPI 是因为它能以较少代码提供请求校验、OpenAPI 和静态资源托管，适合单体 MVP。备选方案是 CLI 或 Streamlit：CLI 不适合非技术用户；Streamlit 上手更快，但 API 契约、错误模型和分层测试边界较弱。React/Vue 独立前端会引入第二套构建链，第一版不采用。

### 2. 用单一查询服务显式编排阶段

查询服务接收问题和请求标识，依次执行：问题校验、指标知识匹配、Schema 选择、Prompt 构建、SQL 生成、SQL 解析与安全校验、超时执行和响应标准化。每个阶段返回类型化结果或领域错误，API 层只负责 HTTP 映射。

这样可用测试替身独立验证编排，避免路由直接拼接现有全局函数。备选是继续在 `main.py` 串联函数，但会把配置、错误处理和测试耦合在入口中。

### 3. 第一版使用同步查询 API

提供 `POST /api/v1/queries`，请求主体至少包含 `question`；成功响应包含 `request_id`、`sql`、`columns`、`rows`、`row_count`、`truncated`、`schema_mode` 和分阶段耗时。错误响应统一包含 `request_id`、稳定 `code` 和中文 `message`。另提供 `/health/live` 与 `/health/ready`。

模型生成和数据库执行在请求生命周期内同步完成，并通过各自超时限制总时长。虽然现有 LLM 客户端已有流式方法，但 SSE 会增加中断、部分 SQL 和前端状态复杂度，且用户只有在完整 SQL 通过安全校验后才能信任结果，因此 MVP 不启用 Token 流式输出。

### 4. SQL 安全使用 AST 白名单与数据库权限双重防护

引入支持 MySQL 方言的 SQL AST 解析器（优先 `sqlglot`），安全层执行：单语句校验、根节点只读校验、危险节点拒绝、表/字段白名单、系统 Schema 拒绝、注释/多语句绕过防护以及明细查询行数上限改写。解析失败默认拒绝，绝不退化为正则放行。

数据库侧使用只读演示账号，并设置连接、读取和语句执行超时。AST 是应用防线，最小权限账号是最终防线。备选方案为正则检查，但无法可靠处理 CTE、子查询、字符串和注释，不满足安全规格。

### 5. 召回层复用现有 Chroma 资产并提供显式回退

把 `table_retriever.py` 与 `field_matcher.py` 包装成 Schema Provider 接口。语义实现负责保证索引可读、召回相关表字段并补充主外键；静态实现返回 `prompt_builder.py` 已定义的五张业务表。应用先尝试语义实现，遇到索引缺失、Embedding 错误或空候选时切换静态实现，响应中设置 `schema_mode=fallback` 并记录原因分类。

`prompt_builder.py` 不再动态导入不存在的 `schema_linker.py`；Schema 文本由调用方显式传入。这样回退是可观察行为，而不是静默吞掉所有异常。第一版继续使用代码/JSON 元数据，不从数据库自动爬取 Schema，以避免权限与元数据质量扩张。

### 6. 配置集中校验，密钥只来自环境

将运行配置收敛为类型化 Settings：模型与 Embedding 配置、数据库连接、允许对象、问题长度、结果上限、超时、日志等级和索引目录。仓库提供 `.env.example`，但不提供可用密码；现有 `root/123456` 默认值必须移除。启动时校验必需配置，日志序列化时统一屏蔽秘密字段。

依赖使用 `uv` 管理并提交锁文件；`pyproject.toml` 区分运行与开发依赖。备选是保留散落的 `os.getenv`，但会让缺失配置延迟到请求阶段才暴露，也难以生成一致的健康状态。

### 7. 演示数据通过 SQL 资产复现

在 `db/` 下提供 Schema、固定种子数据和只读账号授权脚本。种子数据使用稳定主键和 upsert/幂等策略，覆盖当前五张业务表、多个时间区间、币种、地区、产品线和订单状态。初始化流程可以由本地 MySQL 执行；可选 Docker Compose 仅用于便捷启动，不成为唯一运行方式。

选择 MySQL 而不是 SQLite 是为了保持现有函数、日期语法和目标方言一致，避免“测试通过但演示数据库语义不同”。

### 8. Web 前端采用无构建静态资源

使用原生 HTML/CSS/JavaScript，由同一个 FastAPI 服务托管。页面维护当前会话内有限历史，提交时禁用重复操作，成功后展示格式化 SQL 与可滚动表格，失败后按错误码呈现中文建议。结果不写入浏览器持久存储。

该选择牺牲复杂组件生态，换取零 Node 构建依赖和更短的 MVP 路径。若后续出现仪表盘、多页路由或可视化编辑需求，再建立独立前端工程。

### 9. 测试分为确定性门禁与真实模型评估

默认 `pytest` 使用 LLM/Embedding 测试替身，覆盖编排、Prompt、AST 安全、API、数据库适配和回退逻辑；集成测试对隔离的演示数据库运行。真实模型基准作为显式命令运行，锁定模型名、温度和数据快照，并生成 Execution Accuracy、Exact Match 和失败分类报告。

发布门槛按规格设为：确定性测试与安全负例全部通过，真实模型基准执行正确率至少 80%，执行失败率不高于 10%。真实模型具有波动，因此报告必须记录模型、配置、时间和用例版本，而不能把一次结果当成永久保证。

## Risks / Trade-offs

- [OpenAI 兼容服务的模型或 Embedding 行为不一致] → 在启动检查中分别验证 Chat 与 Embedding，记录模型标识，并提供静态 Schema 回退；不把 Embedding 可用性等同于查询服务存活。
- [模型生成语法正确但业务口径错误的 SQL] → 指标知识、Prompt 规则、固定基准集和执行等价评估共同约束；UI 始终展示 SQL，避免把结果包装成不可审查的答案。
- [AST 改写 LIMIT 改变复杂查询语义] → 仅对顶层明细查询改写，聚合查询保持语义；解析或分类不确定时拒绝或使用数据库侧结果截取并标记。
- [同步 API 响应较慢] → 为模型和数据库分别设置超时、显示加载状态并记录阶段耗时；超过本地 MVP 可接受范围后再引入异步作业。
- [Chroma 私有 API 和 LangChain 版本变化] → 将 Chroma 访问封装在适配器中、锁定版本并用集成测试覆盖索引构建和加载。
- [演示数据不足导致准确率虚高或用例无区分度] → 种子数据覆盖相互冲突的状态、币种和维度，并让每个基准问题产生可验证的非平凡结果。
- [本地单用户无认证仍可能被局域网访问] → 默认仅绑定 `127.0.0.1`，README 明确禁止直接暴露公网；远程访问与认证留给后续变更。

## Migration Plan

1. 补齐项目依赖、类型化配置和目录骨架，同时保留现有脚本可运行。
2. 新增 SQL 安全层并修改数据库适配器，使任何执行都先经过安全校验；用测试替身验证后再连接演示数据库。
3. 建立幂等演示数据库和只读账号，运行现有评估器确认基础 SQL 可执行。
4. 封装指标、Schema Provider、Prompt 与 LLM 适配器，建立统一查询服务；删除对缺失 `schema_linker.py` 的隐式依赖。
5. 增加 API、健康检查和静态 Web 页面，将 `main.py` 替换为正式启动入口。
6. 建立确定性测试、基准集和真实模型评估报告，达到验收门槛后更新 README。

回滚时可恢复到变更前提交；数据库初始化仅创建演示 Schema/账号，回滚脚本只针对明确命名的演示对象。任何回滚都不得删除用户自有数据库或未由本项目创建的数据。

## Open Questions

- 首次实现可依据当前开发机条件选择“已有本地 MySQL”或“Docker Compose MySQL”作为主要文档路径，但两者必须使用同一套 SQL 初始化资产，且不会改变对外行为规格。
